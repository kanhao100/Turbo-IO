# 过程：验证应用开发能力，而不是为了固件而固件

## 目标与取舍

目标是回答三个实际问题：官方 OTA 路径能否承载我们的 AP 修改？轻量 BES2800 眼镜能否运行我们增加的页面和交互？能否显示普通 PNG，而不止固定模板文字？成功后应逐渐把这些能力封装为可审查的应用/显示接口，不把频繁刷机当最终使用方式。

初期调查了 LauncherTestImageView / img_test、文件读取与工厂图片线索。**最后公开并实测的 R3 不是把任意文件直接送入那个测试查看器**，而是在菜单末尾建立独立对象，调用原厂 LVGL/PNG 解码显示接口，将小 PNG 随 AP 编入，缩小首次验证范围。

### 为什么坚持只修改 application（`nuttx_ap.bin`）？

这是首次验证的主动取舍，不是认为整个系统只有 AP 有用，也不是认为 AP 改坏了就一定能救回来。

1. **修改位置与目标对应。** 本次需要新增菜单入口、处理页面进入/退出并显示 PNG；所需菜单代码、LVGL 绑定与图片调用位置已经在 AP 中定位。无需为了这个小页面同时修改蓝牙核或恢复组件。
2. **尽量保留原厂基础链路。** BTH、APC1、Recovery、分区表等其余负载保持原字节，避免把通信、安装/恢复和显示改动混在同一次实验里。这里是尽量减少新增风险，不能保证 AP 故障时原厂链路仍可使用。
3. **缩小变量，便于定位与复现。** 除 AP 本体和清单中对应的 Size/Md5 外，其余内容保持不变。可以逐字节证明修改范围，将新增代码、图片、hook 和生命周期作为重点检查对象；出现问题时更容易区分改动来源。
4. **先验证应用能力，不重写整个系统。** 目标是验证“原厂系统上能否增加自己的小页面/眼镜应用”，保留已有功能和正常 OTA 流程。动态传图、通用应用接口与更多 UI 能力留给后续独立实验。

**这里的 application 是 AP 固件镜像，不是像手机 App 一样隔离运行的安全沙盒。** AP 内包含系统运行所需代码；错误指令、内存写入或生命周期处理仍可能拖垮系统，甚至使蓝牙与 OTA 不可用。**只改 AP ≠ 只物理刷 AP ≠ 不会变砖**：我们仍使用包含其他原样成员的完整 OTA，安装器可能重写它们；Recovery 不变也不等于已经验证回滚或救砖。这是减少改动面的策略，不是安全承诺。

## 1. 绑定基线

只用 Strix OS 1.0.4.12，记录原厂 14 负载及清单哈希；原 AP 9,466,560 B，SHA-256 `53afdf5298815849eafca6f315a70606d2a605aff2e563f79050f797d615a988`。先保存原厂成员，构建到新目录，不原地修改。

符号地址不能只凭字符串搜索：从 AP 中复核符号表地址、名称、Thumb 状态和目标指令，再绑定原生函数。公开 metadata 仅保留需要的符号及 hook 附近入口地址，构建仍逐一核对原始字节。

## 2. 菜单与内存生命周期

原菜单容纳七项，不能直接向原七项数组写第八个指针。R3 将对象分配从 `0xdc`（220 B）扩展到 `0xfc`（252 B），原字段偏移不变，尾部追加 32 B 的控制状态/渲染引用。

原第七项（勿扰）稳定停下后，再向后旋转进入独立 Turbo Photo 覆盖层，不把原数组索引改成 7。点击后显示图片；隐藏/退出/销毁释放自有对象，保留原厂唤醒、息屏、返回及其他菜单事件优先级。入口为最小文字标签，未制作图标/动画。

## 3. 普通 PNG 与 AP 修改

图片是 88×98 RGBA8 PNG，4,022 B，非帧缓冲原始位图。复核 PNG 结构/CRC/尺寸，并通过原厂图片解码接口检查解码器类型与对象生命周期；不把 API 成功等同于镜片成功。

最终 AP 为 9,473,376 B，比原厂增加 6,816 B。原有主体仅在白名单位置写入 28 B hook/分配补丁，追加模块、图片和对齐，移动尾部标记；头部和其他原字段保留。未修改 BTH、APC1、Recovery、分区表等其他负载。所有完整成员均重新校验，清单只有 AP 的 Size/Md5 改变。

**MD5/SHA-256 用于确定内容与检测损坏，不是“验证能启动”的证明，也不是厂商签名。** 本次成功不能证明所有启动阶段没有签名验真。

## 4. 离线验证

- 主机 C 状态测试：原七项透传、菜单边界、重复事件、取消、失败回退与 262,144 个长度六事件序列。
- 渲染测试：七类模拟分支（含正常路径），隐藏准备、解码失败、释放、重复释放、资源所有权。
- ARM Unicorn：补丁入口、跳板、寄存器/栈、对象 canary；**原生 LVGL/PNG 和 MPU/启动过程仍是模拟或未覆盖**。
- AP 差异白名单、分区容量、未定义符号、清单 MD5、ZIP 回读、另 13 项不变。
- 手机发送保护本地测试：默认锁定、设备绑定、授权期限、Mode 2 顺序、逐片与冻结副本比对，共 366 个测试片段（不是实际传输片数）。

## 5. 手机到眼镜的官方链路

本次使用官方 **files / Mode 2** 路径，而不是把 ZIP 直接交给眼镜解压：

```text
固定 R3 本机下载源
  → 手机下载 ZIP、检查 MD5、解压并验证 14 文件
  → 电量/空间/空闲等官方预检
  → 人工授权，开始 Mode 2
  → 眼镜请求版本、清单、文件区间
  → 手机按 Name / Start / Size 返回文件切片
  → 眼镜安装阶段、重启
  → 重连、版本验证、真实图片与菜单验收
```

OTA 业务为 9：type 1 OS、2 电量、3 空间、4 开始（Mode 2）、5 版本、6 文件清单、7 文件片段、11 空闲查询。type 9 是眼镜进入安装的通知线索；手机没收到通知不保证眼镜没开始重启。完整 OTA 可能重新写入内容未改的组件，不能说“只物理刷 AP”。

手机研究扩展只让指定 R3 与当前设备通过，发送时逐片比较内存冻结副本。固定下载源只监听 `127.0.0.1`，不暴露公网；允许下载和允许发送是两个不同授权。

## 6. 实际踩过的坑

1. **空闲消息误判**：早期保护漏掉 type 11，未授权开始被挡后，官方恢复查询也被挡，随后出现 `ota_task_in_progress`。此时并未传固件；修复为只放行无 JSON 业务内容且无二进制的空闲查询，并加回归测试。
2. **本机升级源失联**：覆盖安装后短时间重启，旧状态文件显示 running，但新进程请求持续 `connectionError`。重启恢复后才从当前进程确认 HTTP 200、hasUpdate=true 和正确 MD5。端口重绑定问题仍是推断，尚无 errno/压力测试证明永久修复；公开参考必须标注这个缺陷。
3. **不能把准备好等同成功**：先验证手机待传目录，再人工确认，再真实传输；不以进度条、版本号或旧快照替代结果。此次同版本更新后版本字符串不变，新增图片行为才是关键运行证据。

## 7. 真机结果与下一步

用户确认更新完成、图片显示、退出/再次进入正常，其他功能综合反馈正常。菜单缺图标现象仍需定位。未做故障回滚、长期运行、动态蓝牙传图、任意分辨率或视频实验。完整证据边界见 [VALIDATION](VALIDATION.md)。

本次公开原样实验产物和原创研究代码，让开发者从小而可审核的页面/应用功能出发；**不要把首次成功理解成通用刷机工具或成熟固件发行版**。
